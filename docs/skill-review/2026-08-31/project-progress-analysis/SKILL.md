# 项目进展分析

## 目标

把非结构化项目材料解释为稳定、可比较的进展事实，而不是把原文换一种说法。输出用于项目看板、周报分析和后续 Todo 提取，但本 Skill 不直接修改任何数据。

## 适用边界

只有材料存在可验证的项目语境，或用户明确要求按项目整理时使用。普通个人事项、定时提醒、通用问答和无法确认项目归属的讨论不得被强行项目化。项目名不能由模型凭空创建；应来自用户原文、已存在项目或明确授权的新项目名称。

## 事实模型

以 Project 或顶层项目需求为最高层，以可独立推进和验收的 Requirement 或 Workstream 为第二层。每个 Requirement 维护目标或预期结果、负责人、当前状态、进展证据、下一里程碑、风险与依赖。

状态使用语义明确的集合：未开始、进行中、验证中、已完成、待决策、被阻塞。只有交付物或验收结果已出现时才标记已完成；已经实施但效果未确认时标记验证中；只有意向或排期时属于计划，不构成当前进展。

## 分析规则

先识别顶层目标和验收标准，再拆分需求。拆分依据是独立目标、独立负责人、独立交付结果或独立节奏，而不是段落长度。不同目标或不同验收方式的内容不能合并为一个 Requirement。

对每条材料判断它是结果证据、执行状态、计划、决策、风险还是背景。只把结果证据和执行状态写入当前进展；计划进入下一节点；决策保留决策内容及影响范围；风险保留触发条件、影响和依赖；背景只用于理解，不冒充变化。

合并同一事实的重复表达，保留最新且证据更强的版本。新旧记录冲突时保留时间和来源，标注待确认，不静默覆盖。指标必须保留口径、时间范围和比较基线；缺失时只陈述原始值或标记不可比较。

每个 Requirement 的进展摘要采用“当前判断 + 本期有效变化 + 下一验证点”。下一验证点应是可以观察的里程碑或结果，不使用“持续跟进、继续优化”这类不可验收表述。

## 结构化输出

输出 Project、Requirements 和 Evidence。每个 Requirement 至少包含 title、objective、status、progressSummary、owner、nextMilestone、dueDate、risks、dependencies 和 sources；未知字段使用 null 或待确认，不猜测。

若材料不属于项目，返回明确的非项目判断及理由，不构造 Project。若属于项目但无法确认目标项目，只返回候选归属和缺失信息，不写入看板。

## 验证

检查层级是否稳定；每条进展是否能回溯；计划与结果是否分离；状态是否与证据匹配；项目名和需求名是否有来源；风险是否具有具体影响；下一节点是否可验收。通过后再把结构化结果交给项目写入 Tool，Tool 的去重、事务、权限和版本结果才代表真正保存成功。
